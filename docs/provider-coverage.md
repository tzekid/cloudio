Use `cloudio coverage` to summarize the checked-in generated manifests locally, `cloudio coverage tags [all|cloudflare|hostinger]` to review support/mode counts by upstream tag group, `cloudio coverage gaps [all|cloudflare|hostinger]` to rank the next broad unresolved groups by pending read evidence plus pending mutation dry-run evidence, `cloudio coverage levels [all|cloudflare|hostinger]` to review manifest-backed L0/L1/L2 evidence and L3 projection candidates by provider, `cloudio coverage level-tags [all|cloudflare|hostinger]` to review the same evidence by upstream tag group, `cloudio coverage capture-candidates [all|cloudflare|hostinger] [tag-query] [--family <family>] [--plans]` to list generated bodyless read routes still missing L2 capture evidence with required parameter placeholders, no-execute `route capture` templates, and optional nested `will_execute:false` read plans for broad family review before live reads, `cloudio coverage dry-run-candidates [all|cloudflare|hostinger] [tag-query] [--family <family>] [--plans]` to list generated mutation routes still missing dry-run review evidence with required parameter placeholders, request-body content-type/schema metadata, no-execute `route dry-run` templates, and optional nested `will_execute:false` dry-run plans for broad family review, `cloudio coverage workplan [all|cloudflare|hostinger] [--focus all|control-plane] [--family <family>]` to rank unresolved provider tag groups and emit the exact routes/capture/dry-run planning commands for each broad slice, and `cloudio coverage routes [all|cloudflare|hostinger] [tag-query] [--family <family>] [--operation <id>] [--method <method>] [--path <template>] [--support <status>] [--mode <mode>] [--detail]` to inspect exact operations in a provider/tag/status group or by operation ID and method/path. The workplan's `control-plane` focus preserves evidence scoring while filtering to Cloudio-relevant families such as accounts, zones, DNS, SSL/TLS, Access, tunnels, rulesets, logs, cache, security posture, tokens, memberships, Hostinger VPS, billing, domains, hosting, Docker, Reach, ecommerce, Horizons, verification, and provider security surfaces. `--family` narrows that focus to one reviewable family, automatically uses control-plane filtering for workplans, and uses the same app-level classifier to filter exact route, capture-candidate, and dry-run-candidate rows for future web/native UI grouping. The tag-level evidence report is also available as `cloudio coverage levels-by-tag` or `cloudio coverage evidence`; by default it ranks rows with pending read or pending mutation dry-run work; diagnostic-blocked reads and generated Cloudflare dry-run policy are counted as evidence, and `--limit=0` prints closed/evidence-only tag rows too. The detailed route view uses the same generated route parser as generic dispatch and prints path/query/header parameters, parameter schema/style shapes, security alternatives, request-body metadata, and response status/schema metadata. `cloudio coverage plan <provider> --operation <id>` selects one generated route, accepts `--path-param name=value`, `--query-param name=value`, and `--header-param name=value`, enforces generated enum and scalar schema values, and renders a no-execute read request plan or mutation dry-run plan with escaped paths and provider URLs without printing header values. `cloudio route plan|read|capture|dry-run <provider> --operation <id>` exposes that same route contract as the first-class CLI/API boundary: plans are no-execute, reads execute only generated bodyless `GET` routes and print metadata without response bodies, captures execute the same read path while storing redacted `snapshots`/`provider_raw`/audit rows, normalizing stable-ID response items into `cloudflare_resources` or `hostinger_resources`, updating typed `cloudflare_inventory_items` and `hostinger_inventory_items` rows for stable provider resources, and updating high-value typed tables for Cloudflare account/zone/DNS and Hostinger VPS route shapes, paginated captures follow generated optional `page` query parameters for Cloudflare `result_info` and Hostinger `data/meta` page envelopes or generated optional `cursor` query parameters for Cloudflare cursor envelopes with a max-page cap, and dry-runs produce `will_execute:false` mutation plans without live writes. `cloudio evidence capture-summary [all|cloudflare|hostinger]` is the read-only DB/manifest audit view for that route contract: it reports actual `route.capture` gaps while splitting fixture/diagnostic-covered routes from truly unresolved L2 read work. Use `zig build api-summary` to fetch the current public OpenAPI files and print operation/tag/security/live-auth-dispatch/L1-route-dispatch/parameter-shape counts. Use `zig build coverage-manifest` to regenerate `coverage/generated/*.jsonl`, and `zig build coverage-check` to compare checked-in coverage rows with the current official specs. The `zig build` coverage/spec commands are intentionally networked and are not part of normal `zig build test`.

Cloudflare mutation routes are counted as generated dry-run review evidence when the generated route is non-deprecated, routable, and still marked `unsafe_mutation` / `dry_run`. The levels/families/tag JSON exposes that count as `generated_dry_run_policy_evidence`. This does not enable live writes; it only records that generic dispatch can render the route as a validated `will_execute:false` plan for review. Hostinger mutations remain visible in `cloudio coverage dry-run-candidates` until they get explicit fixture/typed dry-run review evidence.

`cloudio coverage workplan --plans` remains no-execute; it appends `--plans` to generated capture and dry-run candidate commands so each selected broad slice points directly at nested read/dry-run plan JSON bundles. `cloudio coverage workplan --bundle --plans --json` expands selected rows with actual capture/dry-run candidate arrays and nested generated plan JSON, capped per tag by `--candidate-limit`, while still reading only checked-in manifests.
`cloudio coverage workplan control-plane` is the positional shorthand for `--focus control-plane`. `cloudio coverage workplan security`, `cloudio coverage workplan hostinger-vps`, and `cloudio coverage workplan hostinger vps` select whole control-plane family slices without tag-string guesswork. `cloudio coverage families control-plane` applies the same positional focus shorthand to the family overview, and `cloudio coverage help` prints the review command grammar.
`cloudio coverage typed-models` ranks tag groups where generic L3 inventory rows exist but typed SQLite projections are missing or thin, with provider/family/focus filters and route/workplan commands for the next broad typed-model slice. `--focus control-plane` shows the required Cloudio L3 modeling backlog, default/all focus also shows optional generic inventory modeling candidates, and JSON rows expose `scope`, `required_for_goal`, and `next_action`. `--include-complete` keeps groups that already have typed-table evidence visible for audit.

`cloudio coverage families`, also available as `cloudio coverage family-summary`, aggregates the same level-tag evidence by provider and Cloudio control-plane family. It is the first stop for selecting broad implementation slices because each row exposes L0/L1/L2/L3 evidence totals, tag counts, priority, and the exact `coverage workplan --family ...` command to drill into the family. Family grouping is owned by `src/app/provider_family.zig` and is reused by coverage routes, workplans, route evidence, and future UI/API grouping instead of being reimplemented per command.

The same checked-in manifests now feed `src/providers/routes.zig`, a provider-neutral internal route metadata library. That module loads Cloudflare and Hostinger routes, exposes operation/path lookup, support/mode/deprecation state, official path/query/header parameter requirements and schema/style shapes, OpenAPI security alternatives, allocation-free `name=value` request parameter parsing, request-body requirements, dry-run-safe body presence/content-type validation, response status/content/schema metadata, response matching for exact codes, status families, and default responses, path-placeholder extraction, required path/query/header validation, generated enum/scalar validation for path/query/header inputs, a reusable request object, escaped path/query rendering, OpenAPI-aware repeated query array serialization, and provider-base URL rendering. Route tests assert that generated OpenAPI path parameters and path-template placeholders match for every checked-in provider route. `src/providers/typed_routes.zig` owns the shared path escaping, optional query rendering, and typed mutation dry-run JSON helpers used by provider-specific route modules so Cloudflare and Hostinger typed dry-run wrappers share the same `will_execute:false` contract. `src/app/provider_family.zig` maps generated provider tags into Cloudio control-plane families, so exact route views, workplans, capture/dry-run candidates, and route evidence all share the same family contract. `cloudio routes --json` exposes the compact route catalog for UI/API callers, and `cloudio routes groups --json` exposes the same L1 contract rolled up by provider and upstream OpenAPI tag with method/mode/support counts, auth requirements, parameter-bearing routes, request-body requirements, and documented response counts. The coverage route detail view reuses this parser and can select exact generated routes by operation ID or method/path, so reviewers see the same route contract that generic dispatch will execute or dry-run. The provider L1 call path is split by responsibility: `src/providers/auth.zig` checks the route security alternatives against Cloudflare token/legacy credentials and Hostinger `apiToken`, `src/providers/request_plan.zig` turns generated route metadata plus caller path/query/header/body inputs into structured no-execute `RequestPlan` and live-read `LiveReadPlan` values with URL, dispatch, and safety-policy evidence, `src/providers/transport.zig` performs bodyless generic live reads by reusing the live-read plan before handing the planned URL to the existing Cloudflare/Hostinger HTTP clients, `src/providers/route_result.zig` matches generated response metadata and renders metadata-only read-result JSON without response bodies, `src/providers/route_plan.zig` renders no-execute JSON request plans and request/response-aware `will_execute:false` mutation plans from the structured request-plan object, and `src/providers/dispatch.zig` remains a compatibility facade over those smaller modules. App route planning, live read metadata, route capture, and dry-run rendering use the owner modules directly. Plans expose `live_call_supported` and `dry_run_supported` dispatch flags so future UI/API layers can present exact L1 behavior without inferring it from support/mode/security fields. Cloudflare dispatch keeps combined and named bearer OpenAPI security alternatives visible in plans and route details while explicitly accepting `bearerAuth` through API-token bearer auth and accepting the combined `api_email+api_key+api_token` shape through either bearer API-token auth or legacy email/global-key auth. This gives future generic dispatch and UI/API layers a broad L1 route contract while hand-written provider clients remain focused on high-value typed wrappers and collectors.

## Status Taxonomy

- `implemented`: Cloudio has a typed or clearly bounded implementation, fixture coverage, and a read-only/manual smoke path when credentials allow it.
- `partial`: Cloudio calls at least one endpoint in the group, but coverage, pagination, models, errors, or tests are incomplete.
- `planned`: Endpoint exists upstream and belongs in Cloudio, but is not implemented yet.
- `blocked_permission`: Endpoint exists but the current token/account/server cannot verify it.
- `unsafe_mutation`: Endpoint mutates remote state and must stay disabled or dry-run until explicit write-mode design exists.
- `deprecated`: Upstream marks the endpoint deprecated.
- `not_applicable`: Endpoint exists but is outside Cloudio's VPS/control-plane scope or has an upstream transport contract Cloudio intentionally does not model.

Generated coverage defaults classify non-deprecated `GET` operations with `requestBody.required=true` as `not_applicable` / `none`, because the generic provider read dispatcher only sends bodyless GET requests. These routes stay visible in coverage manifests with their request-body metadata, but are excluded from generic read execution until Cloudio has an explicit read-with-body transport policy.

Hostinger metrics require `date_from` and `date_to` query parameters. Cloudio currently uses a read-only 24-hour UTC window for refresh and CLI metrics calls.

Generated route rows include `path_params`, `query_params`, and `header_params` arrays with `name`, `required`, OpenAPI `style`, `explode`, schema refs, schema types, formats, and enum values resolved from operation-level, path-level, and shared `components.parameters` OpenAPI definitions. Route rendering validates required, unknown, generated enum-constrained, and generated boolean/integer/number path/query/header parameters, and tests require `path_params` to match the placeholders in each generated path template. String and object-typed params remain permissive so broad L1 planning does not overfit format hints. Repeated query inputs for array params are rendered according to generated style/explode metadata, including comma-separated `form` arrays when `explode=false`; otherwise repeated keys are preserved. Header validation is case-insensitive and generic planners never print header values. Callers can pass those values through one `provider_routes.Request`, keeping generic dispatch and future UI/API code on the same input shape; CLI callers can use the shared `name=value` parser to build the same request shape. Rows also include `request_body`, `responses`, and `security` objects resolved from inline or shared OpenAPI definitions and operation/root security declarations, with required status, status codes, content types, schema refs, auth-required state, and auth scheme alternatives. Generic dispatch rejects protected routes whose official auth alternatives cannot be satisfied by Cloudio's current Cloudflare API-token, Cloudflare email/global-key, or Hostinger `apiToken` auth paths. For Cloudflare only, dispatch recognizes `bearerAuth` as the same bearer-token header transport Cloudio already sends for API tokens, and recognizes the upstream combined `api_email+api_key+api_token` bundle as compatible with either bearer API-token auth or legacy email/global-key auth; the raw named and combined alternatives remain visible in route details and plans. Request body input is represented only as `present` plus optional `content_type`; body contents are never stored in route requests or printed in dry-run plans. Response lookup prefers exact numeric status codes, then `4XX`/`5XX` style family matches, then `default`, and generic read results expose the matched response metadata next to HTTP status and body byte count without printing the raw body. Generic read request plans and mutation dry-run plans include request/response/security/parameter-shape sections plus escaped URLs so L1 contracts remain visible without executing live provider reads or writes or hand-writing one route at a time. Generic route capture now reuses the same L3 resource parsers as the provider collectors, so successful Cloudflare and Hostinger captures update the broad inventory tables whenever redacted response items expose stable IDs, and also upsert selected typed tables for Cloudflare accounts, zones, DNS records, and Hostinger VPS rows. Generic paginated capture requires a generated `page` or `cursor` query parameter and stores each redacted page separately; it recognizes Cloudflare offset `result_info`, Cloudflare cursor `result_info`, Cloudflare root cursor, and Hostinger `data/meta` envelopes, reports the recognized `pagination_envelope`, reports normalized resource and typed row counts, redacts cursor token values from emitted endpoints and audit labels, and stops on non-2xx responses, missing pagination metadata, no next page, or the caller's `--max-pages` cap.

## Coverage Review Gate

Before adding or changing provider behavior:

1. Run `zig build api-summary` and paste the relevant operation/tag delta into the review notes.
2. Run `zig build coverage-manifest` and update the generated provider coverage row before or alongside code changes.
3. Use `cloudio coverage routes <provider> <tag> --detail` to review the generated L1 path/query/header/body/response/security contract and parameter shapes for the whole tag group.
4. Add fixture tests for response parsing and error envelopes.
5. For read-only endpoints, run a smoke command when credentials permit it.
6. For mutation endpoints, implement only a typed dry-run plan until explicit write-mode policy exists. Generated Cloudflare control-plane dry-run evidence is acceptable for L1 review only when the route planner still emits `will_execute:false`.
