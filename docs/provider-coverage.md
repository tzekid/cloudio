# Provider Coverage Baseline

Last checked: 2026-06-17.

Canonical sources:

- Cloudflare API reference: https://developers.cloudflare.com/api/
- Cloudflare OpenAPI schema: https://github.com/cloudflare/api-schemas and https://raw.githubusercontent.com/cloudflare/api-schemas/main/openapi.json
- Hostinger API reference: https://developers.hostinger.com/
- Hostinger OpenAPI schema: https://github.com/hostinger/api and https://raw.githubusercontent.com/hostinger/api/main/openapi.json

Use `cloudio coverage` to summarize the checked-in generated manifests locally, `cloudio coverage tags [all|cloudflare|hostinger]` to review support/mode counts by upstream tag group, and `cloudio coverage routes [all|cloudflare|hostinger] [tag-query] [--operation <id>] [--method <method>] [--path <template>] [--support <status>] [--mode <mode>] [--detail]` to inspect exact operations in a provider/tag/status group or by operation ID and method/path. The detailed route view uses the same generated route parser as generic dispatch and prints path/query/header parameters, parameter schema/style shapes, security alternatives, request-body metadata, and response status/schema metadata. `cloudio coverage plan <provider> --operation <id>` selects one generated route, accepts `--path-param name=value`, `--query-param name=value`, and `--header-param name=value`, enforces generated enum and scalar schema values, and renders a no-execute read request plan or mutation dry-run plan with escaped paths and provider URLs without printing header values. Use `zig build api-summary` to fetch the current public OpenAPI files and print operation/tag/security/live-auth-dispatch/L1-route-dispatch/parameter-shape counts. Use `zig build coverage-manifest` to regenerate `coverage/generated/*.jsonl`, and `zig build coverage-check` to compare checked-in coverage rows with the current official specs. The `zig build` coverage/spec commands are intentionally networked and are not part of normal `zig build test`.

The same checked-in manifests now feed `src/providers/routes.zig`, a provider-neutral internal route metadata library. That module loads Cloudflare and Hostinger routes, exposes operation/path lookup, support/mode/deprecation state, official path/query/header parameter requirements and schema/style shapes, OpenAPI security alternatives, allocation-free `name=value` request parameter parsing, request-body requirements, dry-run-safe body presence/content-type validation, response status/content/schema metadata, response matching for exact codes, status families, and default responses, path-placeholder extraction, required path/query/header validation, generated enum/scalar validation for path/query/header inputs, a reusable request object, escaped path/query rendering, OpenAPI-aware repeated query array serialization, and provider-base URL rendering. Route tests assert that generated OpenAPI path parameters and path-template placeholders match for every checked-in provider route. The coverage route detail view reuses this parser and can select exact generated routes by operation ID or method/path, so reviewers see the same route contract that generic dispatch will execute or dry-run. `src/providers/dispatch.zig` builds on that route contract with provider auth handling checked against the route security alternatives, Cloudflare public reads where the spec permits anonymous access, bodyless generic read calls for `GET`/`read` routes, validated route header forwarding, generated response metadata matching for live read results, metadata-only read-result JSON that does not print response bodies, no-execute JSON request plans for read routes, and request/response-aware `will_execute:false` dry-run plans with full provider URLs for mutation routes without storing or printing body contents. Plans expose `live_call_supported` and `dry_run_supported` dispatch flags so future UI/API layers can present exact L1 behavior without inferring it from support/mode/security fields. Cloudflare dispatch keeps combined and named bearer OpenAPI security alternatives visible in plans and route details while explicitly accepting `bearerAuth` through API-token bearer auth and accepting the combined `api_email+api_key+api_token` shape through either bearer API-token auth or legacy email/global-key auth. This gives future generic dispatch and UI/API layers a broad L1 route contract while hand-written provider clients remain focused on high-value typed wrappers and collectors.

## Status Taxonomy

- `implemented`: Cloudio has a typed or clearly bounded implementation, fixture coverage, and a read-only/manual smoke path when credentials allow it.
- `partial`: Cloudio calls at least one endpoint in the group, but coverage, pagination, models, errors, or tests are incomplete.
- `planned`: Endpoint exists upstream and belongs in Cloudio, but is not implemented yet.
- `blocked_permission`: Endpoint exists but the current token/account/server cannot verify it.
- `unsafe_mutation`: Endpoint mutates remote state and must stay disabled or dry-run until explicit write-mode design exists.
- `deprecated`: Upstream marks the endpoint deprecated.
- `not_applicable`: Endpoint exists but is outside Cloudio's VPS/control-plane scope or has an upstream transport contract Cloudio intentionally does not model.

Generated coverage defaults classify non-deprecated `GET` operations with `requestBody.required=true` as `not_applicable` / `none`, because the generic provider read dispatcher only sends bodyless GET requests. These routes stay visible in coverage manifests with their request-body metadata, but are excluded from generic read execution until Cloudio has an explicit read-with-body transport policy.

Hostinger metrics require `date_from` and `date_to` query parameters. Cloudio currently uses a read-only 24-hour UTC window for refresh and CLI metrics calls.

Generated route rows include `path_params`, `query_params`, and `header_params` arrays with `name`, `required`, OpenAPI `style`, `explode`, schema refs, schema types, formats, and enum values resolved from operation-level, path-level, and shared `components.parameters` OpenAPI definitions. Route rendering validates required, unknown, generated enum-constrained, and generated boolean/integer/number path/query/header parameters, and tests require `path_params` to match the placeholders in each generated path template. String and object-typed params remain permissive so broad L1 planning does not overfit format hints. Repeated query inputs for array params are rendered according to generated style/explode metadata, including comma-separated `form` arrays when `explode=false`; otherwise repeated keys are preserved. Header validation is case-insensitive and generic planners never print header values. Callers can pass those values through one `provider_routes.Request`, keeping generic dispatch and future UI/API code on the same input shape; CLI callers can use the shared `name=value` parser to build the same request shape. Rows also include `request_body`, `responses`, and `security` objects resolved from inline or shared OpenAPI definitions and operation/root security declarations, with required status, status codes, content types, schema refs, auth-required state, and auth scheme alternatives. Generic dispatch rejects protected routes whose official auth alternatives cannot be satisfied by Cloudio's current Cloudflare API-token, Cloudflare email/global-key, or Hostinger `apiToken` auth paths. For Cloudflare only, dispatch recognizes `bearerAuth` as the same bearer-token header transport Cloudio already sends for API tokens, and recognizes the upstream combined `api_email+api_key+api_token` bundle as compatible with either bearer API-token auth or legacy email/global-key auth; the raw named and combined alternatives remain visible in route details and plans. Request body input is represented only as `present` plus optional `content_type`; body contents are never stored in route requests or printed in dry-run plans. Response lookup prefers exact numeric status codes, then `4XX`/`5XX` style family matches, then `default`, and generic read results expose the matched response metadata next to HTTP status and body byte count without printing the raw body. Generic read request plans and mutation dry-run plans include request/response/security/parameter-shape sections plus escaped URLs so L1 contracts remain visible without executing live provider reads or writes or hand-writing one route at a time.

## Coverage Review Gate

Before adding or changing provider behavior:

1. Run `zig build api-summary` and paste the relevant operation/tag delta into the review notes.
2. Run `zig build coverage-manifest` and update the generated provider coverage row before or alongside code changes.
3. Use `cloudio coverage routes <provider> <tag> --detail` to review the generated L1 path/query/header/body/response/security contract and parameter shapes for the whole tag group.
4. Add fixture tests for response parsing and error envelopes.
5. For read-only endpoints, run a smoke command when credentials permit it.
6. For mutation endpoints, implement only a typed dry-run plan until explicit write-mode policy exists.
7. Run `zig build coverage-check` before closing provider work to catch upstream drift.
