Use `cloudio coverage` to summarize the checked-in generated manifests locally, `cloudio coverage tags [all|cloudflare|hostinger]` to review support/mode counts by upstream tag group, `cloudio coverage gaps [all|cloudflare|hostinger]` to rank the next broad unresolved groups, `cloudio coverage levels [all|cloudflare|hostinger]` to review manifest-backed L0/L1/L2 evidence and L3 projection candidates by provider, `cloudio coverage level-tags [all|cloudflare|hostinger]` to review the same evidence by upstream tag group, `cloudio coverage capture-candidates [all|cloudflare|hostinger] [tag-query]` to list generated bodyless read routes still missing L2 capture evidence with required parameter placeholders and no-execute `route capture` templates, `cloudio coverage dry-run-candidates [all|cloudflare|hostinger] [tag-query]` to list generated mutation routes still missing dry-run review evidence with required parameter placeholders, request-body content-type/schema metadata, and no-execute `route dry-run` templates, `cloudio coverage workplan [all|cloudflare|hostinger] [--focus all|control-plane]` to rank unresolved provider tag groups and emit the exact routes/capture/dry-run planning commands for each broad slice, and `cloudio coverage routes [all|cloudflare|hostinger] [tag-query] [--operation <id>] [--method <method>] [--path <template>] [--support <status>] [--mode <mode>] [--detail]` to inspect exact operations in a provider/tag/status group or by operation ID and method/path. The workplan's `control-plane` focus preserves evidence scoring while filtering to Cloudio-relevant families such as accounts, zones, DNS, SSL/TLS, Access, tunnels, rulesets, logs, cache, security posture, tokens, memberships, Hostinger VPS, billing, domains, hosting, Docker, and provider security surfaces. The tag-level evidence report is also available as `cloudio coverage levels-by-tag` or `cloudio coverage evidence`; by default it ranks rows with pending read, diagnostic-blocked read, or pending mutation dry-run work, and `--limit=0` prints closed/evidence-only tag rows too. The detailed route view uses the same generated route parser as generic dispatch and prints path/query/header parameters, parameter schema/style shapes, security alternatives, request-body metadata, and response status/schema metadata. `cloudio coverage plan <provider> --operation <id>` selects one generated route, accepts `--path-param name=value`, `--query-param name=value`, and `--header-param name=value`, enforces generated enum and scalar schema values, and renders a no-execute read request plan or mutation dry-run plan with escaped paths and provider URLs without printing header values. `cloudio route plan|read|capture|dry-run <provider> --operation <id>` exposes that same route contract as the first-class CLI/API boundary: plans are no-execute, reads execute only generated bodyless `GET` routes and print metadata without response bodies, captures execute the same read path while storing redacted `snapshots`/`provider_raw`/audit rows, normalizing stable-ID response items into `cloudflare_resources` or `hostinger_resources`, updating typed `cloudflare_inventory_items` and `hostinger_inventory_items` rows for stable provider resources, and updating high-value typed tables for Cloudflare account/zone/DNS and Hostinger VPS route shapes, paginated captures follow generated optional `page` query parameters for Cloudflare `result_info` and Hostinger `data/meta` page envelopes or generated optional `cursor` query parameters for Cloudflare cursor envelopes with a max-page cap, and dry-runs produce `will_execute:false` mutation plans without live writes. Use `zig build api-summary` to fetch the current public OpenAPI files and print operation/tag/security/live-auth-dispatch/L1-route-dispatch/parameter-shape counts. Use `zig build coverage-manifest` to regenerate `coverage/generated/*.jsonl`, and `zig build coverage-check` to compare checked-in coverage rows with the current official specs. The `zig build` coverage/spec commands are intentionally networked and are not part of normal `zig build test`.

The same checked-in manifests now feed `src/providers/routes.zig`, a provider-neutral internal route metadata library. That module loads Cloudflare and Hostinger routes, exposes operation/path lookup, support/mode/deprecation state, official path/query/header parameter requirements and schema/style shapes, OpenAPI security alternatives, allocation-free `name=value` request parameter parsing, request-body requirements, dry-run-safe body presence/content-type validation, response status/content/schema metadata, response matching for exact codes, status families, and default responses, path-placeholder extraction, required path/query/header validation, generated enum/scalar validation for path/query/header inputs, a reusable request object, escaped path/query rendering, OpenAPI-aware repeated query array serialization, and provider-base URL rendering. Route tests assert that generated OpenAPI path parameters and path-template placeholders match for every checked-in provider route. The coverage route detail view reuses this parser and can select exact generated routes by operation ID or method/path, so reviewers see the same route contract that generic dispatch will execute or dry-run. `src/providers/dispatch.zig` builds on that route contract with provider auth handling checked against the route security alternatives, Cloudflare public reads where the spec permits anonymous access, bodyless generic read calls for `GET`/`read` routes, validated route header forwarding, generated response metadata matching for live read results, metadata-only read-result JSON that does not print response bodies, no-execute JSON request plans for read routes, and request/response-aware `will_execute:false` dry-run plans with full provider URLs for mutation routes without storing or printing body contents. Plans expose `live_call_supported` and `dry_run_supported` dispatch flags so future UI/API layers can present exact L1 behavior without inferring it from support/mode/security fields. Cloudflare dispatch keeps combined and named bearer OpenAPI security alternatives visible in plans and route details while explicitly accepting `bearerAuth` through API-token bearer auth and accepting the combined `api_email+api_key+api_token` shape through either bearer API-token auth or legacy email/global-key auth. This gives future generic dispatch and UI/API layers a broad L1 route contract while hand-written provider clients remain focused on high-value typed wrappers and collectors.

## Status Taxonomy

- `implemented`: Cloudio has a typed or clearly bounded implementation, fixture coverage, and a read-only/manual smoke path when credentials allow it.
- `partial`: Cloudio calls at least one endpoint in the group, but coverage, pagination, models, errors, or tests are incomplete.
- `planned`: Endpoint exists upstream and belongs in Cloudio, but is not implemented yet.
- `blocked_permission`: Endpoint exists but the current token/account/server cannot verify it.
- `unsafe_mutation`: Endpoint mutates remote state and must stay disabled or dry-run until explicit write-mode design exists.
- `deprecated`: Upstream marks the endpoint deprecated.
- `not_applicable`: Endpoint exists but is outside Cloudio's VPS/control-plane scope or has an upstream transport contract Cloudio intentionally does not model.

Generated coverage defaults classify non-deprecated `GET` operations with `requestBody.required=true` as `not_applicable` / `none`, because the generic provider read dispatcher only sends bodyless GET requests. These routes stay visible in coverage manifests with their request-body metadata, but are excluded from generic read execution until Cloudio has an explicit read-with-body transport policy.

Cloudflare implementation must prefer API tokens. Legacy email/global-key auth remains compatibility-only and should be isolated in the provider auth layer.

This is intentionally broad and reviewable: high-value tables such as `hostinger_vps` remain available for stronger typed workflows, while `hostinger_resources` and `hostinger_inventory_items` give future UI/API work normalized inventory surfaces across billing, DNS, domains, hosting, ecommerce, reach, Docker, VPS inventory, and per-VM read groups.

Hostinger metrics require `date_from` and `date_to` query parameters. Cloudio currently uses a read-only 24-hour UTC window for refresh and CLI metrics calls.

Generated route rows include `path_params`, `query_params`, and `header_params` arrays with `name`, `required`, OpenAPI `style`, `explode`, schema refs, schema types, formats, and enum values resolved from operation-level, path-level, and shared `components.parameters` OpenAPI definitions. Route rendering validates required, unknown, generated enum-constrained, and generated boolean/integer/number path/query/header parameters, and tests require `path_params` to match the placeholders in each generated path template. String and object-typed params remain permissive so broad L1 planning does not overfit format hints. Repeated query inputs for array params are rendered according to generated style/explode metadata, including comma-separated `form` arrays when `explode=false`; otherwise repeated keys are preserved. Header validation is case-insensitive and generic planners never print header values. Callers can pass those values through one `provider_routes.Request`, keeping generic dispatch and future UI/API code on the same input shape; CLI callers can use the shared `name=value` parser to build the same request shape. Rows also include `request_body`, `responses`, and `security` objects resolved from inline or shared OpenAPI definitions and operation/root security declarations, with required status, status codes, content types, schema refs, auth-required state, and auth scheme alternatives. Generic dispatch rejects protected routes whose official auth alternatives cannot be satisfied by Cloudio's current Cloudflare API-token, Cloudflare email/global-key, or Hostinger `apiToken` auth paths. For Cloudflare only, dispatch recognizes `bearerAuth` as the same bearer-token header transport Cloudio already sends for API tokens, and recognizes the upstream combined `api_email+api_key+api_token` bundle as compatible with either bearer API-token auth or legacy email/global-key auth; the raw named and combined alternatives remain visible in route details and plans. Request body input is represented only as `present` plus optional `content_type`; body contents are never stored in route requests or printed in dry-run plans. Response lookup prefers exact numeric status codes, then `4XX`/`5XX` style family matches, then `default`, and generic read results expose the matched response metadata next to HTTP status and body byte count without printing the raw body. Generic read request plans and mutation dry-run plans include request/response/security/parameter-shape sections plus escaped URLs so L1 contracts remain visible without executing live provider reads or writes or hand-writing one route at a time. Generic route capture now reuses the same L3 resource parsers as the provider collectors, so successful Cloudflare and Hostinger captures update the broad inventory tables whenever redacted response items expose stable IDs, and also upsert selected typed tables for Cloudflare accounts, zones, DNS records, and Hostinger VPS rows. Generic paginated capture requires a generated `page` or `cursor` query parameter and stores each redacted page separately; it recognizes Cloudflare offset `result_info`, Cloudflare cursor `result_info`, Cloudflare root cursor, and Hostinger `data/meta` envelopes, reports the recognized `pagination_envelope`, reports normalized resource and typed row counts, redacts cursor token values from emitted endpoints and audit labels, and stops on non-2xx responses, missing pagination metadata, no next page, or the caller's `--max-pages` cap.

## Coverage Review Gate

Before adding or changing provider behavior:

1. Run `zig build api-summary` and paste the relevant operation/tag delta into the review notes.
2. Run `zig build coverage-manifest` and update the generated provider coverage row before or alongside code changes.
3. Use `cloudio coverage routes <provider> <tag> --detail` to review the generated L1 path/query/header/body/response/security contract and parameter shapes for the whole tag group.
4. Add fixture tests for response parsing and error envelopes.
5. For read-only endpoints, run a smoke command when credentials permit it.
6. For mutation endpoints, implement only a typed dry-run plan until explicit write-mode policy exists.
7. Run `zig build coverage-check` before closing provider work to catch upstream drift.
